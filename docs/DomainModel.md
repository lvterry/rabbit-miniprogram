# 小兔排课 Domain Model

本文记录已确认的业务模型，作为后续数据库结构与 API 设计的依据。当前小程序仍是使用本地模拟数据的交互原型；本文描述目标业务规则，不以原型的数据字段为准。

## 已确认的规则

- 老师可以先创建学员档案，学员无需当场登录。
- 学员可以通过老师分享的专属邀请，登录小程序并认领自己的档案。绑定后再次登录，自动看到自己参加的课程。
- 一次课可以是 1 小时、2 小时或其他时长。课次记录实际起止时间，但课时余额按**次数**统计：一次需要扣次的预约消耗 1 次，不按时长换算。
- 小组课的一次授课可以有多位学员。预约、出勤和扣次结果按学员分别记录。
- 改期、取消、恢复、完成和撤销操作需要保留历史。课时变动也必须保留流水，不能通过删除旧记录来“恢复”余额。

## 核心实体

| 实体 | 主要职责与建议字段 |
| --- | --- |
| `Account` 登录账号 | 小程序内的账号 ID、微信身份标识 `openid`、创建时间。账号可具有老师身份，也可绑定学员档案；微信密钥仅由服务端保管。 |
| `Teacher` 老师 | 关联登录账号，作为课程、学员档案和业务数据的归属主体。 |
| `Student` 学员档案 | 由老师创建并归属于老师；保存姓名、备注、活跃状态等资料。即使未绑定账号也能选课、排课和记账。 |
| `StudentBinding` 学员身份绑定 | 关联 `Student` 与 `Account`，保存绑定时间、状态及解绑记录。一份有效的学员档案最多绑定一个账号；一个账号可关联多位老师创建的档案。 |
| `StudentInvitation` 学员邀请 | 关联待认领的学员档案，保存随机邀请凭证、有效期、使用状态和创建人。邀请被打开时展示档案信息，由学员确认后完成绑定。 |
| `Course` 课程 | 老师提供的课程项目，如“西语 1 对 1”；保存名称、介绍及启用状态。它不是某天实际上的一节课。 |
| `Enrollment` 选课关系 | 关联学员与课程，保存加入、退出时间及状态；支持学员参加多门课程并保留历史。 |
| `ClassSession` 课次 | 关联课程与老师，保存实际开始和结束时间、地点或授课备注，以及待上课、已完成、已取消等状态。 |
| `Booking` 预约 | 关联一位学员与一个课次，保存该学员的预约、取消、出勤和扣次结果。一节小组课对应多条预约。 |
| `CreditPackage` 课时包 | 可选的销售规格，如“10 次课”；定义名称、次数和参考价格。 |
| `CreditGrant` 课时获取记录 | 记录某位学员购买、获赠或由老师添加的次数，以及来源、获取时间、有效期和备注。可以关联课时包。 |
| `CreditLedgerEntry` 课时流水 | 记录增加、消耗、返还和人工调整的带符号次数、发生时间、原因及关联的获取记录或预约。余额由流水汇总。 |
| `Payment` 收款记录 | 记录收款或退款的金额、时间、状态及关联的课时获取记录；财务报表从有效收款记录汇总。免费赠送课时不要求收款记录。 |
| `SessionEvent` 课次操作记录 | 记录课次的改期、取消、恢复、完成、撤销及备注修改，包含操作者、时间和操作原因。 |

`Account` 是登录身份，`Student` 是老师管理的业务档案。两者不能合并：档案可以先于账号存在，同一登录账号也可能向多位老师学习。

## 主要关系

```text
Account 1 ── 0..1 Teacher
Account 1 ── 0..N StudentBinding N ── 1 Student
Teacher 1 ── N Student / Course / ClassSession
Student N ── N Course                 （通过 Enrollment）
Course 1 ── N ClassSession
ClassSession 1 ── N Booking N ── 1 Student
Student 1 ── N CreditGrant / CreditLedgerEntry
Booking 1 ── N CreditLedgerEntry      （消耗及可能的返还）
CreditGrant 1 ── 0..N Payment
ClassSession 1 ── N SessionEvent
```

同一学员在同一课次至多有一条有效预约。课程、学员、课次和预约均使用稳定 ID 关联；改名不应修改历史记录中的归属关系。展示历史时可另外保存必要的名称快照。

## 业务流程与一致性

### 学员认领

1. 老师创建未绑定的学员档案，并生成专属邀请。
2. 学员通过邀请进入小程序。服务端用微信登录凭证识别当前账号，展示老师与学员档案信息供确认。
3. 确认后，服务端校验邀请仍有效、档案未被他人绑定，再建立 `StudentBinding` 并将邀请标为已使用。
4. 后续登录根据账号查找有效绑定，学员只能读取所绑定档案允许展示的数据。

邀请凭证应不可猜测，具有有效期和使用次数限制，并支持老师重新生成、解除错误绑定。仅打开邀请不能直接认领，以免转发后被误绑。

### 排课与扣次

- 老师创建课次，再为参加该课次的每位学员建立预约。一对一课也保留独立预约，以统一处理扣次。
- 完成课次时，对每条应扣次的预约分别写入 `-1` 的课时流水；若取消时选择扣次，也写入 `-1`。不扣次的取消不产生消耗流水。
- 撤销完成或恢复已扣次的取消课次时，写入关联原消耗的 `+1` 返还流水。课次状态、预约结果、流水与操作记录应在同一业务事务中更新。
- 同一操作重复请求不能重复扣次或返还；API 需要幂等保护。余额不足时是否允许完成并产生负余额，留待 API 规则确定。
- 实际授课时长保存在课次中供展示和排课使用，不参与次数换算。

### 收款与报表

- 增加课时与收款是不同事实：赠送或人工添加课时可以没有付款，收款也可能发生在实际授课之前。
- 收入报表按有效收款及退款汇总，不根据课次完成数或课时消耗数推算收入。
- 退款是否同时收回未使用次数属于独立业务操作，需要分别留下金钱与课时记录。

## 当前版本的产品假设

这些假设与现有交互一致，后续可调整，不阻碍上述实体设计：

1. **老师负责排课和修改预约；学员先只读。** 学员可查看自己的课程、预约和剩余次数，不可查看老师内部备注、其他学员资料或财务数据。
2. **余额在同一老师名下按学员汇总。** 暂不限制某笔课时只能用于某门课程；若以后需要专课专用，可在获取记录和消耗规则上增加课程范围。

待确定的细则：学员是否可自行发起预约；余额不足时的处理；课时有效期及到期规则；一笔付款与多笔课时获取记录的关联方式。这些应在对应 API 实现前明确。
